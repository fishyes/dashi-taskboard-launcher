# v1.21.1

## Changes

- **Codex guard defaults aligned with the latest subagent practice**
  (`src-tauri/src/codex_guard/guard_schema.json`, 18 → 19 entries):
  - **No longer manages `features.multi_agent_v2.enabled` and
    `features.multi_agent_v2.tool_namespace`**: the current practice's
    `[features.multi_agent_v2]` table carries only
    `hide_spawn_agent_metadata`, `expose_spawn_agent_model_overrides`, and
    the three wait timeouts. Both removed keys are still valid in codex
    0.153.2 (verified against upstream `MultiAgentV2ConfigToml`), so configs
    already containing them keep working; the guard simply stops writing or
    enforcing them.
  - **`agents-v1-remove` no longer deletes the whole `[agents]` table**:
    the old entry applied `toml_absent` to `agents` itself, which — since
    v1.21.0 moved valid keys into that table — would also delete the
    guard-managed `agents.enabled` and
    `agents.max_concurrent_threads_per_session`. It is now four per-key
    `toml_absent` entries: `agents.max_threads` (v1 alias of the concurrency
    key; conflicts if both are set), `agents.max_depth`,
    `agents.interrupt_message`, and
    `features.multi_agent_v2.max_concurrent_threads_per_session` (the
    pre-v1.21.0 location of the concurrency limit, default 7 — the limit now
    lives only at `agents.max_concurrent_threads_per_session`).
  - The AGENTS.md「子代理使用」block and `agents/default.toml` defaults were
    re-verified byte-identical against the current practice (unchanged).
- Smoke fixtures and docs follow the schema: the locked-param fixture and
  its assertion reference `agents.max_concurrent_threads_per_session`, the
  `toml_absent` mock targets `agents.max_threads`, and CONTEXT.md's path
  examples describe per-key cleanup instead of whole-table removal.

## Upgrade notes

- Existing installs whose on-disk schema copy
  (`~/.codex-pro-max/codex-guard-schema.json`) still holds the old entries
  keep them per the disk-overrides-builtin merge rule. In particular the old
  `agents-v1-remove` disk entry still targets the whole `[agents]` table —
  delete the stale entries in the guard UI (or sync the file) instead of
  applying them. The three renamed/new cleanup entries take effect
  immediately for configs without a disk copy.
